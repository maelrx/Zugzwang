# ZGW-0108 — Arena: jogar no tabuleiro contra os modelos (setup via UI)

## Status

In progress (2026-09-08). Diretiva direta do operador (Mestre Mael): criar uma
feature no webapp para jogar contra os modelos com todo o setup selecionável
pela UI. Alvo validado: `gemini-3.8-flash-low` (adapter
`provider.antigravity_cli`), melhor resultado empírico até agora (parity com
SF-1320, 2 vitórias por mate nos full games R1).

## Escopo

- **NÃO é run canônico nem benchmark**: sessão interativa local (127.0.0.1),
  rotulada "Arena". Nenhum artefato canônico é escrito; nenhum gate de
  experimento é declarado. As chamadas de provider são 100% registradas
  (pedido/resposta/uso/latência) em JSONL imutável — o invariante de
  atribuição se aplica por chamada, não por run.
- **NÃO publica no snapshot do viewer** (`regen-snapshot.sh` intocado). O modo
  Jogar é self-contained no webapp.

## Requisitos

- R1: serviço local `zugzwang_cli.arena` (HTTP stdlib, sem dependência nova):
  - loop de decisão nativo equivalente ao `chess.cognitive_navigation`
    (mesmo protocolo de wire: system prompt, `board_*` tools,
    `board_finalize` no ROOT, pacote L0 real via `ChessPerception` +
    `StandardChessRulesKernel`, preload do root, child packages inline);
  - reuso integral dos adapters de provider (mesmos construtores de
    `durable_services`): `antigravity-cli` (validado), `opencode` (muse),
    `codex-cli`;
  - legalidade/estado sempre server-side (python-chess via kernel do
    zugzwang-chess); a UI nunca decide legalidade;
  - persistência por jogo em `out/arena/`: `game.json` (estado),
    `calls.jsonl` (evidência bruta de cada chamada), `game.pgn`.
- R2: modo "Jogar" no viewer-next (main + worktree de aparência 4190):
  - setup completo via UI: provider/modelo/esforço, cor do humano, rounds,
    ascii, plies de histórico, diretiva opcional;
  - tabuleiro interativo (chessground) com dests do servidor; promoção
    perguntada; painel de evidência por lance (latência/tokens/rounds/texto);
  - `gemini-3.8-flash-low` aparece marcado **validado**;
  - proxy `/play` → serviço da arena no vite (porta 4191).
- R3: validação ponta a ponta real com `gemini-3.8-flash-low`: criar jogo,
  lances humanos reais, resposta legal do modelo, evidência gravada.
- R4: suíte offline verde (testes novos com backend fake), ruff, pyright.

## API (local)

- `GET  /play/api/providers` — catálogo com flag `validated`.
- `GET  /play/api/games` — lista de jogos.
- `POST /play/api/games` — cria jogo (setup completo); se o modelo for as
  brancas, o turno dele dispara em background.
- `GET  /play/api/games/{id}` — estado completo (dests quando é a vez do
  humano; `thinking` quando o modelo está jogando).
- `POST /play/api/games/{id}/moves` — lance humano `{uci}`.
- `POST /play/api/games/{id}/retry` — repetir turno do modelo após erro de
  provider (nunca conta como lance).
- `POST /play/api/games/{id}/resign` — desistência humana.

## Gates

- G1: validação offline limpa (pytest unit+integration novos, ruff, pyright,
  format).
- G2: validação real `gemini-3.8-flash-low` (R3) com evidência em
  `out/arena/`.
- G3 (humano): Mestre Mael joga de fato pela UI e ratifica a experiência.

## Decisões pré-tomadas (autoridade do operador, chat 2026-09-08)

- Feature autorizada diretamente pelo Mestre Mael (autoridade humana final),
  contornando a moratória genérica de Web UI: a UI do viewer-next já é
  oficial (ZGW-0102) e esta ordem delimita o modo Jogar como acréscimo local.
- Somente chamadas reais durante a validação G2 (opt-in explícito do
  operador). Testes offline nunca chamam provider.

## Não-objetivos
